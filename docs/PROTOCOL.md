# DOS <-> Bridge wire protocol

The DOS client never talks to Home Assistant directly (no TLS on real-mode
DOS). Instead it speaks a tiny plain-text, line-oriented protocol to the
bridge service, which does the real HA REST calls. The same protocol runs
identically over:

- **TCP** (mTCP on the 3Com EtherLink III, port 6321 by default)
- **Serial** (RS-232, default 9600 8N1, or configurable)

This lets the DOS client use one code path (`protocol.c`) regardless of
transport — only `net_tcp.c` / `net_serial.c` differ underneath.

## Framing

- ASCII text, one command or reply per line.
- Lines end with `\r\n`.
- Max line length: 200 bytes (DOS-side buffers are fixed at 256).
- No binary data, no JSON — keeps the DOS-side parser trivial (strtok on `|`).
- Multi-line replies end with a lone `END\r\n`.

## Commands (DOS -> bridge)

| Command                | Description                                   |
|-------------------------|------------------------------------------------|
| `PING`                  | Liveness check.                                |
| `LIST`                  | List configured entities.                      |
| `GET <entity_id>`       | Get current state of one entity.               |
| `ON <entity_id>`        | Call `turn_on`.                                |
| `OFF <entity_id>`       | Call `turn_off`.                                |
| `TOGGLE <entity_id>`    | Call `toggle`.                                  |

## Replies (bridge -> DOS)

| Reply                                   | Meaning                              |
|-------------------------------------------|----------------------------------------|
| `PONG`                                    | Reply to `PING`.                       |
| `ENTITY\|<id>\|<friendly_name>\|<state>`  | One row of a `LIST` reply.             |
| `END`                                     | Terminates a `LIST` reply.             |
| `STATE\|<id>\|<state>`                    | Reply to `GET`.                        |
| `OK`                                      | Command succeeded (`ON`/`OFF`/`TOGGLE`).|
| `ERR\|<message>`                          | Command failed; message is one line, no `\|`. |

## Example session

```
> LIST
< ENTITY|light.kitchen|Kitchen Light|on
< ENTITY|light.hallway|Hallway Light|off
< ENTITY|switch.fan|Office Fan|off
< END
> TOGGLE light.hallway
< OK
> GET light.hallway
< STATE|light.hallway|on
```

## Design notes

- The bridge is authoritative on which entities exist — configured via
  `bridge/config.ini` (`[entities]` section), not auto-discovered, so the
  DOS-side list is predictable and short (a 486 text screen only fits so
  many rows anyway).
- Every reply line is generated by the bridge, never proxied raw from HA, so
  HA's actual JSON/TLS never has to be understood by DOS.
- The bridge treats TCP and serial connections identically: same command
  parser, same handler functions, just a different `Transport` read/write
  implementation in Python.
